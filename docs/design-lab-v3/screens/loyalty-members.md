# V3 art direction: Members, member detail and recording

By Astra, TapMart's design director.

**Two seconds.** Find the name. See the remaining visit. Count once. If the reward is ready, redeem it without losing the member or source.

**Signature.** The acquisition thread survives the counter transaction: Sara’s fourth mark becomes a fifth, then a redeemed reward, while Joined from Jasmine stays attached. A standalone loyalty product would not connect that return to its original TapMart campaign.

## States

- 01, Roster, default: All selected, ten records, compact progress, no contacts, portraits, source paragraphs or engagement scores. On desktop Sara is the initial read-only inspected member; phone remains a list.
- 02, Roster lookup and filters: query matches normalized first name, phone or email locally. All, Repeat visitors and Reward ready are mutually exclusive status filters; an incoming source filter intersects them. Clear filters removes the source/status restriction. Typing does not change focus or create events.
- 03, Roster empty/error variants: distinguish no members, no query matches, no ready rewards, no repeat visitors and invalid member URL. A live-zero program offers View QR. No-program and draft contexts show their setup guards.
- 04, Redemption-event view: view=redemptions shows individual reward-use events, newest first. A member can appear more than once if they have multiple redemption events. This is not labelled as a unique-member total.
- 05, Member detail, collecting: first name and mask; current progress; five strokes or one points line; reward; primary Add visit or Add points; preserved source thread; Wallet summary; collapsed History. Sara starts at 4 of 5.
- 06, Member detail, zero/ready/redeemed: zero retains Add visit; ready makes Redeem primary and Add visit secondary; redeemed retains its status until the next counted activity and allows Add visit. A ready instance and additional progress can coexist.
- 07, Member disclosures: source opens immutable evidence; Wallet opens the current read-only concept; History expands counted and uncounted events. Member actions exposes only the honest Send update and Block boundaries.
- 08, Recording entry: Scan is default unless the last explicitly used mode was Search. A member query parameter is honored only following an explicit staff action. Opening the counter performs no recording.
- 09, Scanner idle: labelled empty coded aperture, Sample member selector, Simulate scan and No camera is used. The default sample is Sara.
- 10, Search mode: aperture and sample selector are replaced by the labelled input and local results. Results contain first name, masked contact and progress. Selecting one enters the same recognition state as scanning.
- 11, Recognition: member identity and QR are stable; progress and Free coffee precede +1 visit. Points shows 1 point, Per qualifying purchase and Add 1 point. The action is usable immediately, before the recognition animation ends.
- 12, Ordinary counted result: commit the event and derived state atomically; replace the action with Visit counted. or Point added.; update the final value once. Show Wallet update simulated only for saved-Wallet projections. Done, Next customer and View member remain.
- 13, Reward unlock: qualifying activity creates an earned instance. The last stroke completes and Reward ready replaces the ordinary caption. Redeem becomes available immediately. It never activates automatically.
- 14, Same-day result: an explicit fresh counting attempt appends a zero-delta event and shows Already counted today., the unchanged value and the daily rule. No progress movement, reward mutation, Wallet update or recent-list reorder occurs.
- 15, Unknown QR: reject the sample without displaying a person. Search members changes mode; Try another QR restores the scanner.
- 16, Recording failure: show the failure in the action region, retain member and request key, and offer Try again. The QA scenario fails the first commit only; the deliberate retry can succeed.
- 17, Redemption confirmation: bind to one ready earned-instance ID, show the exact reward and no-visit consequence, then Cancel or Redeem reward. Repeated activation of the same request is idempotent.
- 18, Redemption complete: consume only that instance’s attached credits, append the redemption event and display Reward redeemed. Retain next-cycle progress and any other ready instances. Wallet and source identity remain.
- 19, Redemption error/stale state: failed mutation leaves the ready instance unchanged. An already-consumed instance returns This reward is no longer ready. rather than creating a second event.
- 20, Next customer: clear recognized identity, result receipt and request key; return to the selected Scan or Search mode. Clear the search query for privacy. Keep the current demo day.
- 21, Focused exit: Done or Close returns to the exact originating roster/detail position. Browser Back first closes a confirmation or disclosure, then the counter. Fixture state remains.
- 22, Lab scenarios: replacement contexts are explicit and confirmed. Advance demo day changes the business calendar day without resetting progress. No hidden clock progression or automatic replay occurs.
